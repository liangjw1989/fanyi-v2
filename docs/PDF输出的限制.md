# 关于 PDF 输出的限制（务必先读）

## 一、为什么"选 PDF"曾经会得到一个 `.html` 文件

**浏览器里没有中文字体文件**，所以网页无法自己写出能正确显示中文的 PDF。

- 自己写 PDF：只能用 PDF 内置的 14 个基础字体（Helvetica 等），
  **不含任何中文字形**，中文全部会变成 `?`。我实测过这条路，不可用。
- 嵌入中文字体：一个 CJK 字体要 8~15 MB，每翻译一篇就产出十几 MB 的 PDF，不现实。
- **唯一可行的办法**：借助浏览器的**打印引擎**（它用系统字体渲染），
  也就是"生成网页 → 打印 → 另存为 PDF"。

所以选 PDF 时会打开一个打印窗口，这是**技术必然**，不是偷懒。

### 现在做了什么改进

| 之前 | 现在 |
|---|---|
| 打印对话框里默认文件名是 `xxx.html`，保存后变成 `xxx.html.pdf` | **文件名预填 `xxx.pdf`**，直接保存就是对的 |
| 还要自己点页面里的"打印"按钮 | **自动弹出打印对话框**，只需按保存 |
| 打印页面上还有按钮和工具栏（会被打进去） | 自动打印时**隐藏工具栏** |

> 如果打印对话框里文件名没预填，手动把结尾的 `.html` 删掉再保存即可。

## 二、为什么有些 PDF 翻译出来"不理想"

这要分两种情况，**必须区分清楚**，否则会一直在错的方向上优化。

### 情况 A：文字层本身不可用（扫描件 / 图片型 PDF）

特征：整页是图片，没有可提取的文字。
**能识别**：`node test/tools/pdf-kind.js <文件.pdf>` 会报告"图片型 PDF"。
**怎么办**：用界面上的**图片模式**（走 OCR）。排版只能靠 OCR + 结构推断，不可能 1:1。

### 情况 B：文字层完整，但结构太碎（本项目的真实短板）

**实测某篇综述 PDF（Biomolecules 2023）**：

```
压缩流分析结果：
  BT (开始文字块)   : 233 个
  TJ (显示文字数组) : 2739 个
  文字相关指令合计  : 3083
  → 文字层完好，不是扫描件
```

但翻译出来的中文里出现了**句子被截断**、**夹进 Creative Commons 许可证文字**等现象。
原因不在引擎，而在**版式还原这一层**：

- 这类期刊 PDF 的文字被切成**极碎的片段**（一个词甚至一个字符一个对象），
  且每页有 380+ 个字体对象（多个子集混排）。
- 碎片越细，"哪些碎片属于同一段、同一栏、同一页"的推断就越容易错。
  一旦行分组或分栏判断偏移，整页的**阅读顺序就会乱**，表现为"句子被拦腰截断"、
  "页脚文字混进正文"。

**这是 PDF 格式的固有限制**，任何工具都无法保证 100% 正确
（PDF 里没有任何"段落""分栏""表格"的语义，只有一堆带坐标的字符）。

### 情况 C：PDF 是多份文档拼接而成

有些下载的 PDF 其实是「正文 + 补充材料 + 版权页」拼在一起的
（该项目实测到 **4 个 `/Pages` 根对象**，说明由多份 PDF 合并而来）。
这种情况下页码、阅读顺序会更乱，属于上游文件本身的组织方式问题。

## 三、怎么办（按效果排序）

| 优先级 | 做法 | 效果 |
|---|---|---|
| ⭐⭐⭐ | **用原始 `.docx` 翻译** | Word 里有真正的段落/表格/分栏结构，能接近 1:1 还原，不存在碎片问题 |
| ⭐⭐ | 换一篇**文字层规整**的 PDF 试试 | 可先跑 `pdf-kind.js` 与 `analyze-pdf-streams.js` 判断 |
| ⭐⭐ | 用 **HTML / 上下对照**输出，而不是纠结 PDF | 这两种输出保留结构最好，且能直接阅读 |
| ⭐ | 扫描件走**图片模式（OCR）** | 内容能拿到，但排版是重建的 |

**最实在的建议**：论文若是从 Word 投稿的，**直接用 `.docx` 原件翻译**。
你反馈的三篇论文，如果都能拿到 Word 原稿，排版问题会基本消失。

## 四、自己判断一个 PDF 值不值得翻译

```bash
cd 最终\repo

# 1) 是扫描件还是文字版？
node test\tools\pdf-kind.js 你的.pdf

# 2) 文字层是否完整？（看 BT / TJ 数量与判定结论）
node test\tools\analyze-pdf-streams.js 你的.pdf

# 3) 在真实浏览器里抽取，看每页文字项与坐标（需要 Edge）
node test\tools\build-harness.js 你的.pdf test\out\tl harness.js 2
powershell -File test\tools\check-text-layer.ps1 -Pdf 你的.pdf -MaxPages 3
```

判定标准（`analyze-pdf-streams.js` 会直接给结论）：

| 结果 | 含义 | 建议 |
|---|---|---|
| `文字块数量正常` | 文字层可用 | 可以翻译，结构问题属情况 B |
| `文字块极少 + 大量图片` | 扫描件 + 残缺 OCR 层 | 走 OCR 模式 |
| `几乎没有文字绘制指令` | 纯图片 PDF | 必须 OCR |

## 五、一句话总结

**PDF 不是"文档"，而是"打印结果"。** 它能被提取的只有字符坐标，
没有段落、没有分栏、没有表格。所以：
**能拿到 Word 就用 Word；只有 PDF 时，接受"版式接近但不保证一致"这个前提。**

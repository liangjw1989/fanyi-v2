# 实测记录：为什么标记会丢，以及怎么保住的

这份文档记录的是**在真实云函数 + 真实翻译引擎上测得的结果**，不是推测。
所有结论都可以用 `test/tools/` 里的脚本复现。

---

## 一、问题的根源：机器翻译会吃掉标记

项目要用"标记包裹文本"的办法来保证**一段一段对应**和**符号原样保留**。
但实测发现，**腾讯云机器翻译会随机丢弃这些标记**。

### 1. 哪种标记格式能活下来（`test/tools/probe-marker-formats.js`）

| 标记格式 | 腾讯云 | DeepSeek |
|---|---|---|
| `⟦0⟧`（原方案） | ✗ 丢 1 个 | ✓ 完整 |
| `[[0]]` | ✗ 丢 1 个 | ✓ 完整 |
| `{{0}}` | ✗ 丢 1 个 | ✓ 完整 |
| `<0>` | ✗ 丢 1 个 | ✗ 丢 4 个 |
| **`##0##`** | **✓ 完整** | **✓ 完整** |
| `\u0001 0 \u0001`（控制字符） | ✗ 全丢 | ✗ 全丢 |

**结论**：`##0##` 是最可靠的格式 → 已改为传输层统一使用它。

### 2. 但 `##0##` 也不是万无一失

严苛测试（9 个真实排版场景）里仍有 2 个丢失，而且原因很具体：

```
输入: ##V0##共纳入 4441 例患者，见表 1。##V0##
输出: There are a total of 4,441 patients included in the study... ##V0##

输入: ##V0##BMI 为 ##P0##kg/m²。##V0##
输出: The BMI is ##P0## kg/m². ##V0##            ← 句首的 ##V0## 没了
```

**规律**：
- **句首的标记**经常被丢（引擎似乎会"修剪"开头的非文字内容）
- 文本里出现 **`²` 这类上标字符**时，也容易连带丢标记
- 同样的输入**重发一次，往往就保住了**（随机性）

### 3. 还有限流问题（会让段落"没翻译"）

```
"##V0##第二组##V0##" → tencent: Your current request times equals to `5` in a second,
                                which exceeds the...
```

腾讯云限制 **5 次/秒**。逐段翻译时如果发得太快，超限的请求直接失败，
前端拿到的是"这一段没翻译"，而且**看起来像成功**（没有报错）。

---

## 二、解决方案（三层防护）

```
第 1 层  传输层换格式      ⟦V3⟧/⟦P0⟧/⟦T1⟧  →  ##V3##/##P0##/##T1##
                          （提高引擎保留率；对端解码后仍是原格式）

第 2 层  逐批校验 + 自适应降级
                          每批翻译后核对标记数量；一旦发现丢失：
                          · 该批改用「逐段翻译」（请求里只有一个片段，
                            标记由程序自己加，物理上不可能丢）
                          · 连续 2 批丢失 → 判定该引擎不可靠，
                            后续全部逐段，不再浪费时间重试

第 3 层  单段重试         某段译文里占位符缺失时，单独重译这一段
                          （最多 2 次，只采用"丢得更少"的结果）
```

另外在**云函数里加了 QPS 节流**（腾讯云 5 次/秒 → 间隔 260ms；
百度免费版 1 次/秒 → 间隔 1100ms），把限流失败挡在服务端，
不再出现"悄悄没翻译"。

## 三、验证结果（真实腾讯云引擎）

### 合成论文稿（19 个片段，含表格 + 各种统计量）

```
片段 19 / 翻译 19 / 兜底 0
保护符号 20 / 术语 2 / 占位符丢失 0
引擎丢标记批次 3 → 自动降级逐段 → 单段重试 → 最终零丢失

✓ 抽查的 8 类符号全部原样保留：
  4441 / 0.001 / 95%CI 1.030~1.074 / OR=1.052 / kg/m² / [1,2] / DFI / 20~59
✓ 表格保持 4 列 × 3 行，表头与单元格译文正确
✓ 标题层级、作者行、摘要段落均正确翻译
```

### 修复前后对比

| 项目 | 修复前 | 修复后 |
|---|---|---|
| 腾讯云 + 标记 | 直接失败或静默丢符号 | 自动降级，**零丢失** |
| `95%CI 1.030~1.074` | 引擎会整块删掉 | 重试后保住 ✓ |
| 表格短单元格 | 限流导致没翻译 | 云端节流后全部翻译 ✓ |
| 目标语言 `zh-CN` | `不支持的语种：en_to_zh-CN` | 已映射为 `zh` ✓ |

## 四、怎么复现这些测试

```bash
cd 最终\repo

# 1) 离线自检：不联网、不花钱，验证整条链路
node test\selfcheck.js

# 2) 标记格式体检：引擎升级后可以重跑，看哪种格式还能活
node test\tools\probe-marker-formats.js

# 3) 真实后端验收：用你的云函数跑一份合成论文稿，检查符号/表格/是否真的翻译了
node test\tools\verify-cloud.js https://你的云函数地址 tencent
node test\tools\verify-cloud.js https://你的云函数地址 baidu
node test\tools\verify-cloud.js https://你的云函数地址 deepseek
```

`verify-cloud.js` 会打印：片段数、翻译数、兜底数、接口调用数、
保护符号数、**占位符丢失数**、引擎丢标记次数、逐段兜底片段数，
并逐项检查 8 类关键符号是否原样保留、表格列数是否不变。

## 五、对使用者的实际影响

| 场景 | 表现 |
|---|---|
| 用腾讯云 / 百度（普通翻译） | 会自动逐段翻译，**比批量慢**（每段约 0.2~0.3 秒），但符号与排版**有保障** |
| 用 DeepSeek（AI 智能翻译） | 标记保留率最高，通常走批量，速度快 |
| 一篇 100 段的论文 | 腾讯云约 40~70 秒，DeepSeek 约 20~40 秒 |
| 翻译记忆命中后重译 | **0 次接口调用**，几乎瞬间完成 |

> 如果对速度敏感、且不介意符号偶有闪失，可以在界面上关掉「符号保护」，
> 这样就不需要标记，批量翻译速度最快 —— 但数字、单位、上下标就不再受保护了。
> **不建议**：论文翻译里这些恰恰是最不能错的部分。

---

## 六、一句话总结

**机器翻译靠不住的不是"翻译"，而是"老实保留标记"。**
所以本项目不再依赖它自觉，而是：**能批量就批量，一发现标记被动过就退回逐段，
逐段还丢就重试，最终由程序保证符号与排版一定对得上。**

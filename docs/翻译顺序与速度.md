# 翻译顺序与速度说明

## 一、默认翻译顺序（每一步都是按顺序、逐段推进）

```
1. 解析文件 → IR（段落/标题/表格/图片 + 字号/对齐/缩进）
2. 逐段查翻译记忆 ── 命中就跳过（0 次调用）★ 这是最快的路径
3. 未命中的段落：先做保护
     · 术语 → ⟦T0⟧ 占位符（按你的术语表强制统一译名）
     · 数字/单位/统计量/上下标/文献编号 → ⟦P0⟧ 占位符
4. 分批打包（默认每批约 4000 字符），把 ⟦⟧ 换成引擎友好的 ##V0## 形式
5. 逐批调用云函数 → 腾讯云 / 百度 / DeepSeek
6. 每批回来先核对标记数量：
     · 缺标记 → 该批改用「逐段翻译」（逐段时没有标记，不可能丢）
     · 连续多批缺标记 → 后续全部逐段
7. 逐段还原占位符（把 ⟦P0⟧ 换回 4441、kg/m²、95%CI…），写回原骨架
8. 发现某段占位符缺失 → 单独重译这一段（最多 2 次，只取更优结果）
9. 生成的译文存进翻译记忆
10. 按原骨架输出 Word / HTML / 中英对照 / 纯文本
```

**顺序要点**：**先记忆 → 再保护 → 再翻译 → 最后还原**。
所以同一篇文件翻第二遍几乎瞬间完成（提示里会显示"N 段记忆复用、0 次调用"）。

## 二、为什么有时偏慢

慢 **不是**因为程序在磨蹭，而是被两件事限住了：

### 1. 腾讯云/百度会"吃掉"分段标记 → 只能逐段翻译

实测：腾讯云的机器翻译会**随机丢弃**文本里的标记，尤其是**标记和占位符紧挨着**时：

```
输入: ##V0####P0##共纳入 4441 例患者##
输出: （开头的 ##V0####P0## 被删掉了）
```

一旦标记丢了，这一批的分段就对不上，程序只能**改成逐段翻译**（一段一次调用）。
逐段是"物理上不可能丢符号"的做法，代价是**调用次数 = 段落数**。

### 2. 腾讯云限制 5 次/秒

逐段翻译时每分钟最多约 300 次调用；云函数里做了节流，避免"部分段落没翻译"。
所以一篇 100 段的论文，用腾讯云大约需要 **40~70 秒**。

### 对比：DeepSeek 更快

DeepSeek 能稳定保留标记（实测 10/10 通过），所以走**批量翻译**：
一次调用翻一整批（默认约 4000 字符），调用次数只有腾讯云的 1/5 ~ 1/10。
一篇 100 段的论文大约 **20~40 秒**，而且译文质量更好。

| 引擎 | 标记保留 | 实际策略 | 100 段论文大致耗时 |
|---|---|---|---|
| 腾讯云 | 随机丢（尤其标记紧邻占位符） | 逐段 | 40~70 秒 |
| 百度 | 同腾讯云（机器翻译通病） | 逐段 | 40~70 秒 |
| **DeepSeek** | 稳定保留 | **批量** | 20~40 秒 |
| 任意引擎 + 记忆命中 | — | 不调用 | 1~2 秒 |

**想快就用 DeepSeek，或者对同一篇文件重译（记忆复用）。**

## 三、已做的提速优化

| 优化 | 效果 |
|---|---|
| 批量上限 2600 → **4000 字符** | 批量模式下调用次数减少约 1/3 |
| 引擎可靠性记忆（会话内） | 已判定不可靠的引擎，后续文档**不再从头踩坑** |
| 重试策略调优 | 批量重试从 2 次降到 1 次，失败 2 批即停止尝试批量，避免白等 |
| 丢占位符的单段重试 | 只在该段真的丢了符号时才触发（多数情况不触发） |
| 逐段间隔 260ms → **120ms** | 真正的限流交给云函数服务端做，前端不再人为拖慢 |

### 实测数据（19 段合成论文稿，腾讯云引擎）

| 版本 | 接口调用 | 耗时 | 占位符丢失 |
|---|---|---|---|
| 优化前 | 22 | 23.7 秒 | 1 |
| **优化后** | 22 | **22.1 秒** | **0** |

耗时基本由"腾讯云必须逐段 + 每次往返约 0.5 秒"决定，这是外部限制。
真正能大幅提速的是换 DeepSeek（走批量）。

## 四、你还能自己选的两档

| 模式 | 怎么做 | 特点 |
|---|---|---|
| 批量优先（默认） | 什么都不用改 | 先试批量，失败自动逐段，速度与正确性平衡 |
| 全部逐段（最稳） | 调用 `translateIR` 时传 `mode: 'safe'` | 完全不依赖引擎保留标记，最可靠但最慢 |

界面上关掉「符号保护」也能变快（不需要标记，直接批量），
但**数字、单位、上下标、术语就不再受保护** —— 论文翻译不建议这么做。
